Design — Section 1: Database Schema

What gets deleted, what gets kept, what gets added.

🗑 Deleted

matters — gone entirely (clientName, matterNumber, opposingParties — all legal-specific)

✅ Kept (unchanged)

tenants — id, name, slug, orgTokenHash, adminTokenHash, plan, subscriptionStatus…
policies — id, tenantId, version, policyJson (JSONB), publishedAt

✨ New tables

divisions
id · tenantId · name · slug · createdAt
"Corporate Law", "Litigation", "Engineering" — org units within a company
teams
id · tenantId · divisionId · name · slug · createdAt
"M&A Team", "Contract Review" — groups within a division
members
id · tenantId · email · displayName · role (super_admin | division_admin | member) · adminDivisionId (nullable) · createdAt
Employees of the tenant. Separate from auth tokens — these are the people the extension enforces policy on
member_teams
memberId · teamId
Many-to-many: one person can be on multiple teams
subjects
id · tenantId · divisionId (nullable = global) · name · description · active · createdAt
Replaces "matters". A named sensitive context: "Zuckerberg Contract", "Project Zeus". divisionId = null means it applies globally across all divisions
rules
id · tenantId · subjectId · kind (keyword | pattern | entropy | score) · keywords[] · pattern (regex) · destinations[] · action (warn | block) · message (custom warning text) · active · createdAt
The actual detection logic. Stored relationally so the admin UI can list/edit/filter them. The policy compiler reads these rows and builds the versioned JSONB snapshot.

How it compiles

The policy compiler (already exists) reads all active subjects + rules for a tenant, organises them by division, and writes a versioned JSONB snapshot into the policies table. The extension fetches that snapshot. Nothing changes in how the extension syncs — only how the data is authored.
