Design — Section 3: Two Critical Flows

How employees join, and how policy gets from the admin UI to the extension.

Flow 1 — Employee joins via extension

First-time install
1 CISO generates a join code for the company in the admin UI (e.g. ACME-7X4K). Shares it with employees via Slack/email.
2 Employee installs extension → popup asks for their work email + join code.
3 Extension calls POST /v1/auth/join → backend creates a member record, assigns them to the tenant's default team, returns an org token + memberId.
4 Extension stores org token locally. Syncs the compiled policy. Starts enforcing rules immediately.
5 CISO sees the new member appear in the admin UI → moves them into the right division/teams.

Flow 2 — Policy change reaches the extension

Admin edits a rule → employee's extension updates
1 Admin adds a new Subject + Rule in the admin UI (or via AI chat).
2 Admin clicks Publish → POST /v1/policy/publish → the policy compiler reads all active divisions, subjects, and rules from the DB, builds a structured JSON, and writes a new versioned snapshot into the policies table.
3 Each employee's extension polls GET /v1/policy/version every 30 min (existing alarm). Detects new version → fetches GET /v1/policy → updates local ruleset.
4 The compiled policy includes each member's team memberships → the extension knows exactly which subjects and rules apply to this specific user.

What the policy compiler changes

Currently it reads from matters and builds fuzzy dictionary rules from opposing-party names. After the redesign: it reads from subjects + rules tables, groups them by division scope, and outputs the same JSONB format the extension already understands. The extension sync mechanism is unchanged.
